# Три слоя и id

Читать перед созданием нового контент-типа или изменением схемы id/реестра.

## Три слоя данных

| Слой | Что | Где живёт | Кто владеет |
|---|---|---|---|
| **SO (авторинг)** | `ScriptableObject`-определения, иммутабельны в рантайме | `Assets/_Project/Scripts/Data/Definitions/*.cs` + `.asset` | этот скилл |
| **Baked POCO (сим)** | чистый C#, снапшот SO на старте боя | `Guildmaster.Combat` | combat-sim (контракт — здесь) |
| **DTO (диск/сеть)** | плоская сериализуемая форма для сейвов/реплеев/Workshop | сериализационный слой | save-system (форма — здесь) |

**Связь между слоями — только строковый id `domain.name`.** Никогда прямой object-ссылкой:
прямая ссылка не переживает сеть/сейв/пересборку и убивает детерминизм. POCO держит id и, при
необходимости, разрешает его через `IContentDatabase` на старте (не в тике).

Общий родитель контент-SO — `ContentDefinition`. Все наследники получают id-инфраструктуру
бесплатно.

## ContentDefinition: базовый класс

`Assets/_Project/Scripts/Data/Definitions/ContentDefinition.cs`:

- Хранит сериализованный `_id` (строка), публичное `Id => _id`.
- `OnValidate` **одноразово** заполняет пустой id из имени ассета через `ContentDomains.MakeId`.
  После заполнения имя и id больше НЕ синхронизируются — иначе rename ассета ломал бы сейвы.
- Кнопка **Edit Id** разблокирует правку через `EditorUtility.DisplayDialog` с предупреждением
  «id попадает в сейвы/реплеи/Workshop — менять безопасно только до выхода контента в мир».
- `protected SetId(string)` — для рантайм-создания def'ов (`CreateRuntime`) и editor-миграций,
  НЕ для геймплейной логики.

Наследуешь новый контент-тип → наследуй от `ContentDefinition` (или от `UnitData`, если это боевой
кит). Ничего в id-механике переопределять не нужно, кроме `OnValidate` (вызвать `base.OnValidate()`).

## Жизненный цикл id (ContentDomains)

`Assets/_Project/Scripts/Data/Definitions/ContentDomains.cs`:

- **`domain` — из ЗАКРЫТОГО словаря** `Domains` (тип → префикс). На сейчас 14 доменов: `relic`,
  `enemy`, `vessel`, `effect`, `tag`, `trait`, `consequence`, `ai_preset`, `guildmaster`, `item`,
  `run_mod`, `encounter`, `battle_preset`, `event`.
- Наследники резолвятся по ближайшему зарегистрированному предку (`RelicData`/`EnemyData` → домен
  своего типа, не `UnitData`).
- `GetDomain(type)` **бросает**, если домена нет: отсутствие маппинга = ошибка конфигурации, не
  тихий дефолт.
- `MakeId(type, assetName)` = `{domain}.{ToSnakeCase(assetName)}`; `"IceChainsStun"` →
  `effect.ice_chains_stun`. `ToSnakeCase` даёт только `[a-z0-9_]`.

**Новый контент-тип → СНАЧАЛА добавь его в `ContentDomains.Domains`.** Без домена `OnValidate` не
заполнит id, а валидация упадёт с «No content domain registered». Это первый шаг, не последний.

## Реестр: IContentDatabase / ContentRegistry

`IContentDatabase.cs` — единственный шов между кодом и контент-ассетами:

```
T    Get<T>(string id)              // бросает при отсутствии (отсутствие контента = ошибка)
bool TryGet<T>(string id, out T)    // мягкий вариант
IReadOnlyList<T> All<T>()           // все определения типа T
```

`ContentRegistry` — рантайм-реализация: словарь `id → ContentDefinition`, построенный один раз из
`ContentDatabase` при сборке DI-контейнера (VContainer `RegisterInstance`). В конструкторе **кидает**
на пустой id и на дубликат id — то есть реестр сам по себе часть валидации.

**Правило:** геймплей берёт контент ТОЛЬКО отсюда. Никаких прямых `[SerializeField] RelicData` в
игровой логике и `Resources.Load`. SO остаётся чистыми данными, реестр — точкой доступа.

## Source-namespace: шов под моды (заложен, не построен)

Моды/Steam Workshop — планируемая, но не ближайшая цель. Схему id под них НЕ раздуваем сейчас:

- **Авторинг-id остаётся `domain.name`** для своего (core) контента — без namespace-префикса.
- Полный ключ под моды = `{source}:{domain}.{name}`, где `source` по умолчанию `core` и
  **опускается** для первопартийного контента. Мод получает свой `source` при загрузке — так мод
  не может молча затенить core-id.
- Это шов на уровне РЕЕСТРА (`IContentDatabase`), не в каждом id. Добавить source-измерение позже —
  локальная правка реестра, потому что весь доступ уже идёт через него (правило 4 из SKILL).
- **Версию в id НЕ кладём.** id — стабильная идентичность, переживающая версии контента.
  Несовместимый редизайн = НОВЫЙ id (осознанно), а версионирование живёт в DTO (`schemaVersion`
  на сейве), не на контент-id.

Пока моды не в работе — просто держи весь доступ через реестр и не раздавай прямых ссылок. Этого
достаточно, чтобы шов остался дешёвым.

## Дисциплина сериализации при рефакторинге

Unity матчит сериализацию по именам — молчаливый rename обнуляет данные в ассетах без ошибки
компиляции. Потому:

- **Переименование сериализованного поля** → `[FormerlySerializedAs("_oldName")]`.
- **Rename/перенос типа под `[SerializeReference]`** (полиморфные данные, напр. компоненты
  `EffectData`) → `[MovedFrom(...)]`. Без него `[SerializeReference]`-данные молча обнуляются.
- **Перенос поля в базовый класс** безопасен при сохранении имени (прецедент — поля кита
  перенесены из `RelicData` в `UnitData` без смены имён).
- **Массовая правка формы существующих ассетов** — editor-миграцией (образец
  `Data/Editor/Migrations/Phase4Package*Migration.cs`), не hand-YAML: Unity перезапишет ручной YAML
  при следующем импорте.
