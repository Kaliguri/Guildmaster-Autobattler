# Сверка с кодом и лечение дрейфа

Сердце скилла. Читать перед любым обновлением факта в `10-reference`/`20-explanation`.
Здесь — как сверять доку с живым кодом и как лечить систематические болезни дрейфа.

## Принцип: код — источник правды

tech-вика описывает **реальный код**, не замысел и не память. Поэтому любой факт перед
фиксацией сверяется с живой реализацией. Порядок доверия:

1. **Живой код** (`Read`/`Grep` по `Assets/_Project/Scripts/`) — истина.
2. Docstring/комментарий в самом классе — почти истина (иногда сам дрейфует, сверять с телом).
3. `tech-changelog` — что и почему решали (но проверить, не `superseded` ли).
4. Планы `40-planning`, старые доки, **моя память** — гипотеза, НЕ истина. Обязательно сверить.

**Не уверена — не пишу.** Несверенный факт в reference хуже пустоты: он врёт с видом истины,
и следующий читатель (человек или агент) строит на нём.

## Чем сверять

- **`Read` / `Grep`** — базовый инструмент: прочитать реальный класс, найти сигнатуру/имя.
- **`unity_reflect`** — когда нужен факт о типе/членах, которого не видно грепом (сгенерированное,
  наследование, атрибуты).
- **`run_tests`** — когда факт о поведении (тик-ордер, инвариант); тест подтверждает, что
  описанное реально исполняется.
- **`context7`** — для API внешних пакетов (Unity, VContainer, UniTask, NGO…): не писать по
  памяти про чужой API, свериться с актуальной докой.

## HARD: `40-planning` = архив замысла

Планы — исторические документы «как мы думали на момент фазы». В них правлю **только
статус-шапки** (что реализовано / отложено / закрыто). Имена классов, интерфейсов, схемы
внутри тела плана **не переписываю** — даже если код давно другой.

- Пример: план Фазы 3 описывает `IUnitBrain`/`ProfileBrain` определённым образом — если
  код разошёлся, актуальное пишется в `reference`/`explanation`, а план остаётся слепком.
- Исключение — **дефект, не замысел**: битая ссылка, сломанный markdown, неверный путь.
  Это чинится (не является следом мысли).
- Живые имена «как есть» синхронизирую только в `10-reference`/`20-explanation`.

*Почему:* переписать план под текущий код = стереть эволюцию «почему пришли к этому».
Ценность планов — именно в исходном замысле; актуальное состояние живёт в reference.

## Систематические болезни дрейфа (чек-лист)

Аудит tech-вики (2026-07-16) выявил повторяющиеся паттерны — искать их первыми:

1. **Устаревшие статус-шапки.** Реализованное числится «ТЗ / план к исполнению / код не
   написан». Лечение: сверить с кодом, шапку → `Реализовано`/`ready`, frontmatter `status`
   синхронизировать с телом.

2. **Устаревший тик-ордер.** Порядок систем в описании расходится с реальным. Сверять с
   боевым циклом в коде. Реальный порядок (на момент аудита — ПЕРЕПРОВЕРЯТЬ по коду, не
   копировать вслепую):
   `ApplyCommands → Brain → Ability → Movement → Displacement → Separation → SpatialHash →
   AutoAttack → Projectiles → Regen → Effects → Drain → Death → CheckOutcome`.

3. **Мёртвые классы в описаниях.** Имена, которых в коде уже нет. Известные замены (сверять,
   не подставлять на веру):
   - `TargetingSystem` → `BrainSystem` / `ProfileBrain`
   - `DamageCalculator.RollCrit` → **вырезан** (крита нет)
   - `BattleSetupBuilder` → `EncounterLoader`
   - `DamageNumber(Spawner)` → `FloatingText`
   - `ContentManagerWindow` → Content Hub
   Мёртвые имена чиню в `reference`/`explanation`; в `40-planning` — не трогаю (правило выше).

4. **«Пакет позже», а он уже стоит.** Доки числят установленное как будущее. Сверять с
   `Packages/manifest.json` и `Assets/Plugins/`. Пример: FMOD/Localization/Addressables
   живы; сейв реально `JsonFileSaveService` (JsonUtility), Easy Save 3 установлен но отложен.

5. **Материальный дрейф (близко к переписыванию раздела).** Раздел описывает архитектуру,
   которой в коде нет вовсе (напр. вымышленный полиморфный AI-граф вместо реальных
   параметризованных пресетов). Лечение: снести вымышленное, написать по docstring/коду
   реального класса. Это самый дорогой случай — сверять построчно.

## Процедура сверки

1. Найти затронутые доки (по теме изменения кода): reference + explanation.
2. Для каждого факта — открыть реальный класс, сверить имя/сигнатуру/поведение.
3. Разошлось → починить в reference/explanation (не в planning).
4. `status` → `ready` если сверено; `updated` → дата.
5. Значимое расхождение/решение → запись в `tech-changelog`.

## Гид по дрейфу внутри самой вики

Если существует док-самоотчёт о техдолге (историч. `code-guide/07. Техдолг` вёл реестр
X1–X3) — он готовый чек-лист «что уже известно как разошедшееся». Проверять его первым.
