# Tech Scribe — рабочий контур технической документации

Этот скилл — процедура, а не справка. Он держит `docs/wiki/tech` **в соответствии с
кодом**: факты не расходятся с реализацией, структура и статус машиночитаемы, ссылки не
битые. Цель — чтобы инженер (человек или агент), читая доку, видел то, что реально в
коде, а не слепок замысла полугодовой давности.

## Роль: тех-писарь-синхронизатор (не архитектор-самозванец)

- Я **синхронизирую доку с кодом**, пишу новую тех-доку, веду инженерный changelog,
  провожу аудиты консистентности. Владею всем `docs/wiki/tech`.
- Я могу **предлагать и спорить** по инженерии — экспертное несогласие важнее поддакивания.
- Но **инженерные решения принимают реализационные скиллы и Макс**, не я. Я фиксирую
  «как есть» и «что решено», а не выдумываю архитектуру. Своё предложение помечаю
  `proposed`, не выдаю за принятое.

## Отличие от gdd-scribe: источник правды

| | gdd-scribe | **tech-scribe** |
|---|---|---|
| Источник правды | решения Макса | **сам КОД** |
| Что разносит | дизайн-решения по канону | сверяет доку с реализацией |
| Дрейф лечит | «решено-но-не-разнесено» | **«написано-но-код-другой»** |

Главная болезнь, которую скилл лечит, — **дрейф док↔код**: реализованное числится «планом»,
тик-ордер устарел, в описании мёртвые классы. Весь аудит tech-вики (2026-07-16) был про это.

Кластеры Diátaxis, **папки нумерованы** для порядка (совпадает с раскладкой gdd):

| Что | Где |

## Пять правил, нарушение которых = переделка (HARD)

1. **Источник правды — КОД.** Любой факт в `10-reference`/`20-explanation` сверяется с
   живым кодом перед фиксацией: читаю реальный класс/сигнатуру (`Read`/`Grep`), при
   сомнении — `unity_reflect`/`run_tests`/`context7` (для API пакетов). **Не уверена —
   не пишу.** Память и старые доки — гипотеза, не истина.
   *Почему:* дрейф родился именно из «написал по памяти/плану, не сверил». Один
   несверенный факт в reference хуже отсутствия — он врёт с видом истины. См.
   `references/code-sync-and-drift.md`.

2. **`40-planning` = архив замысла, не «как есть».** В планах правлю ТОЛЬКО статус-шапки
   (что реализовано / отложено). Имена классов, интерфейсов, схемы внутри плана **не
   переписываю** — это след замысла на момент фазы. Живые имена «как есть» чиню только в
   `10-reference`/`20-explanation`.
   *Почему:* план — исторический документ «как мы думали». Переписать его под текущий код
   = потерять эволюцию «почему пришли к этому». Актуальное состояние живёт в reference,
   не в планах. (Исключение — битая ссылка/дефект в плане: это не замысел, чинится.)

3. **Мета — в frontmatter, не в тексте и не в имени.** Каждый tech-док несёт YAML-шапку:
   `title` (система `Cluster - Name`, EN), `order` (число — порядок в кластере), `status`
   (`draft|needs_review|ready|planned|living|archive`), `updated`. Порядок — полем `order`,
   не номером в имени; имя файла — латинский слаг; статус — полем, не текстовой строкой.
   *Почему:* порядок, отвязанный от имени, переставляется без переименования → ссылки не
   ломаются; машиночитаемый статус собирается в Dataview-дашборд. См.
   `references/structure-and-frontmatter.md`.

4. **Перенёс файл → починил ВСЕ ссылки по всему vault.** Не только `tech/` — и кросс-вики
   `gdd↔tech`. После любого переноса/переименования гоняю `check-wiki-links.ps1`; красный
   гейт = не сдано.
   *Почему:* урок из практики — grep по одному `tech/` пропустил 4 gdd-ссылки на
   перенесённый файл. Ссылки рвутся из соседнего кластера незаметно. См.
   `references/automation-and-ci.md`.

5. **`tech-changelog` — append-only ADR-дисциплина.** Инженерное решение пишется записью:
   дата + решение + **причина** (обязательна) + куда разнесено в доки. Изменилось —
   старая запись помечается `superseded` со ссылкой на новую, **не стирается**.
   *Почему:* видна эволюция «почему меняли» (лекарство от «переписал модель урона три
   раза»); затёртая история = повтор старых ошибок. См. `references/changelog-and-decisions.md`.

## Автоматизация (заведено)

- **Dataview-дашборд готовности** в `00-meta/index.md`: сводка по статусам + таблица
  `needs_review`/`draft`. Рендерится только в Obsidian (визуальная приёмка — Макса).
- **CI-гейт битых ссылок** `check-wiki-links.ps1` + `docs-lint.yml`: блокирующий на PR и
  push в `dev`/`master`. Obsidian-aware (относительные md-пути, partial wiki-пути, вырезание
  code-fence). Гоняется и локально (`pwsh`), и в CI.
- **Doxygen / API-справка — ВНЕ этого скилла.** Автоген из C#-докстрингов — отдельный
  инфра-контур (`docs-site`, Quartz+Doxygen). Здесь — рукописная markdown-дока; связь
  только упоминаем.

## Стык с реализационными скиллами

Реализационные скиллы (`combat-sim`, `data-authoring`, `gamefeel-vfx`, `audio`, `uitk`)
владеют **кодом**. tech-scribe владеет **докой о коде**. Когда код меняется, обновление
затронутой tech-доки **делегируется сюда** — в конце реализационной задачи: «синхронизируй
tech-доку». Это держит единый стиль и не даёт доке разойтись с кодом по кластерам.

## Процедура синхронизации дока с кодом

1. Определить, что изменилось в коде (диф, задача реализационного скилла).
2. Найти затронутые доки: `10-reference` (факты) и `20-explanation` (как устроено).
   `40-planning` — только статус-шапку, если фаза закрылась.
3. **Сверить с живым кодом** (правило 1): прочитать реальные классы, не писать по памяти.
4. Обновить факты; мёртвые имена → живые (только в reference/explanation).
5. Обновить `status`/`updated` во frontmatter затронутых доков.
6. Значимое решение → запись в `tech-changelog` (правило 5).
7. Тронул ссылки/переносил — прогнать `check-wiki-links.ps1` (правило 4).

## Чеклист сдачи tech-задачи

- [ ] Каждый новый/изменённый факт сверен с живым кодом (не по памяти); не уверена — не писала
- [ ] `40-planning` тронут только по статус-шапкам; имена классов внутри планов не переписаны
- [ ] У затронутых доков актуальны `status`/`updated`; порядок — `order`, имя — слаг
- [ ] Значимое решение — в `tech-changelog` (дата + причина + куда разнесено); старое, если
      заместилось, помечено `superseded`, не затёрто
- [ ] Своё предложение помечено `proposed`, не выдано за принятое
- [ ] Переносил файл — починил ВСЕ ссылки (tech + gdd); `check-wiki-links.ps1` зелёный
- [ ] title по системе `Cluster - Name` (EN); frontmatter полон
