## Зачем это вообще

Три жалобы Макса (06.08.2026, дословно): «упускаешь 70% важного, не проверяешь себя, не понимаешь
что я от тебя прошу»; «нет единого цельного набора всех элементов, их состояний»; «часто
встречаются очень старые состояния кнопок и решения, от которых мы отказались».

Разбор показал, что все три — не про старательность, а про три дыры инфраструктуры.

**Дыра 1. Перечня состояний не существует нигде.** `components.uss` — 3994 строки одной лентой,
~30 интерактивных классов, у каждого случайный набор. `:checked` не объявлен **ни разу** (галочка
в настройках визуально не отличается включённой от выключенной). `:active` нет у 12 кликабельных
классов, `:focus` — у 13, `:disabled` есть у 11 из ~30. Три разных «таба» с тремя разными наборами:
`.gm-tab` (5 состояний), `.gm-filter-tab` (наследует чип), `.gm-runbar__tab` (одно — только
наведение). Двенадцать классов состояний код вешает, а USS их не рисует. Документации по состояниям
нет: `ui-feedback.md` объявлен домом для «доступно/недоступно/занято/выбрано», держит только
«недоступно».

**Дыра 2. Зеркала нет.** `UiPreviewCatalog` показывает 7 позиций из 14 контролов, и таб в нём собран
другим способом, чем в игре (`new Button` + класс против `gm:PlateButton`) — то есть состояния
активного таба там не работают вовсе. 05.08 стенд выведен из процедуры («решает живая игра»), взамен
не появилось ничего. Плюс состояния в обычный скриншот не попадают: наведение и нажатие надо чем-то
вызвать, а форсировать псевдосостояние в UI Toolkit Debugger нельзя — подтверждённая дыра Unity.

**Дыра 3. Отменённое лежит вперемешку с живым.** Регистр «лист» отменён 03.08, а `.gm-panel--sheet`
с пергаментом стоит на четырёх живых экранах. `ui-visual-language.md` со `status: living` описывает
отменённое. `closed-forks.md` числит бой за меню отклонённым, хотя он в игре. `UI/AGENTS.md`
описывает пять несуществующих сущностей. 20 классов в USS без потребителя, 12 селекторов объявлены
дважды.

Внешняя каноника подтверждает механику дыры 3: модель разрешает конфликт источников тем, что берёт
**найденный первым**. При смеси живого и мёртвого это не лечится вниманием.

## Вердикты Макса по развилкам (06.08.2026)

| Развилка | Решение |
|---|---|
| Раскладка `components.uss` | **Блок на файл + экран на файл.** `Theme/components/*.uss` по BEM-блоку, `Theme/screens/*.uss` по экрану |
| Отменённый регистр «лист» | **Снять.** Четыре экрана уходят в стекло; фактура, `.gm-panel--sheet` и запекатель — из дерева |
| Обязательный набор состояний | **hover + active + disabled + focus**, `checked` где применимо. `focus` — ради клавиатуры и геймпада (Steam Deck) |
| Порядок работ | **Сначала инфраструктура**, экран настроек после неё и первым потребителем |
| Бой за главным меню | Сначала отклонён, потом опробован и **оставлен**. Правда — «принято», `closed-forks` врёт |

## Фазы

Порядок несущий: реестр — источник для контактного листа и для гейтов, поэтому он первый; глаза
(контактный лист) идут раньше гейтов, чтобы правки состояний было видно, а не только слышно от теста.

**Порядок поправлен по ходу 06.08:** контактный лист (Ф3) сделан ДО резки USS (Ф2). В исходном плане
он стоял после, и это противоречило собственному же требованию «снимать лист до и после резки» —
резать 3994 строки вслепую значило узнать о поломке от Макса.

**Сделано 06.08:** Ф1 (реестр, 36 записей), Ф3 (контактный лист, 11 кадров), Ф4 (гейт состояний +
гейт порядка ярусов), Ф2 (31 файл, доказано попиксельно: 11 кадров из 11 совпали с дорезочной
темой). Гейт красный на 50 дырах — это Ф5.

### Ф1. Реестр компонентов и состояний

Плоская таблица как **данные**: блок → его классы-модификаторы → обязательные состояния → флаг
«интерактивный». Живёт C#-таблицей в рантайм-сборке `Guildmaster.UI` (не JSON и не SO): её читают
трое — тест, редакторный инструмент и витрина, — а ошибку в ней должен ловить компилятор. Правка
компонента и правка реестра уезжают одним диффом.

Наполнить по 14 контролам плюс по блокам без контрола (`.gm-card`, `.gm-arcana-card`,
`.gm-picker__row`, `.gm-shop__card` и родня).

- [ ] `UiComponentRegistry` заведён, наполнен, покрыт быстрым тестом на непустоту и уникальность

### Ф2. Раскладка USS

`components.uss` → `Theme/components/*.uss` (button, plate, tab, chip, panel, slot, card, tooltip,
row) + `Theme/screens/*.uss` (settings, loadout, mainmenu, shop, reward, event, hub, profile,
console). Подключение — только через тему, не через `<Style src>` в UXML: иначе каскад начнёт
зависеть от порядка открытия экранов.

По ходу: снять 12 дублей селекторов (консоль и пикер получили внутри себя повторные блоки) и 20
классов-сирот.

Готча: при равной специфичности выигрывает импортированный позже — порядок `@import` несущий и
фиксируется тестом, а не договором.

- [ ] Файлы разнесены, `theme.uss` собирает цепочку
- [ ] Дубли и сироты сняты
- [ ] Тест фиксирует порядок `@import`

### Ф3. Контактный лист состояний

Редакторный пункт `Alebardium → UI → Contact Sheet`. В play строит из реестра оверлей-витрину поверх
живой панели, **форсирует псевдосостояния рефлексией** (`VisualElement.pseudoStates` — internal, но
пишется; проверить на 6000.4), снимает `ScreenCapture` и гасит себя. Кадр честный: настоящая тема,
настоящая панель, настоящий масштаб.

Это и мои глаза перед показом, и приёмка Макса одним взглядом. В чат уходит через `SendUserFile`.

- [ ] Форс псевдосостояний проверен на нашей версии Unity
- [ ] Пункт меню снимает лист по всему реестру
- [ ] Лист показан Максу

### Ф4. Гейты

Быстрые тесты (мимо редактора, текстовый разбор USS):

1. интерактивный блок из реестра имеет **все** обязательные состояния в USS;
2. класс, который вешает C# литералом `gm-*`, имеет правило в USS;
3. класс в USS имеет потребителя в UXML или C#;
4. порядок `@import` в `theme.uss` не менялся.

- [ ] Четыре теста написаны, красные по факту (это и есть список работ Ф5)

## Что НЕ входит в заход

- Постобработка UI через RenderTexture — открытая развилка, вердикта нет.
- Раскладка мета-экранов (единое окно / лист по контенту) — развилка сформулирована через отменённую
  метафору, переформулируется отдельно.
- Лавка — единственный экран захода 05.08 без вердикта.
- Компоненты раскладки (`Stack`/`Section`) из фазы 3 плана дизайн-системы — отдельный заход, иначе
  этот не кончится.
