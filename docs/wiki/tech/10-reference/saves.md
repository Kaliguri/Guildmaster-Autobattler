## Принцип

Сохранение привязано к **хосту**: файл сохранения хранится у него и синхронизируется через **Steam Cloud** (Auto-Cloud по маске файлов — путь сейвов фиксируется с самого начала).

> **Host migration (решение):** бесшовная передача хоста в реальном времени **не делается** к фестивалю (это непросто в NGO) — отложена на post-release. Текущая модель: если хост выходит, сессия завершается, последний автосейв расшарен через Steam Cloud, и другой игрок **перехостит и загрузит** с последней точки. Опирается на частые автосейвы на границах ивентов (ниже).

## Точки автосохранения

**Сверено с кодом 2026-07-26.** Прежняя формулировка «три точки» устарела: `RunStateService.Autosave()`
вызывается из **девяти** мест — `GameFlow` (старт акта, после узла, конец акта), `ActRunner`
(ход по карте, поражение), `ShopController` (покупка, продажа, реролл), `RewardPresenter`,
`EventEffectApplier`, `DeploymentController` (правка расстановки).

Фактическая политика — **«сохраняем после каждого значимого изменения забега»**, и она принята
как целевая: запись атомарна и стоит килобайты, а цена пропущенной точки — потерянный ход игрока.

## Формат хранения (решение)

- **Бэкенд — `JsonFileSaveService`** (`JsonUtility`, файл в `persistentDataPath`) за интерфейсом `ISaveService`: наш собственный и **единственный**. Запись атомарна (временный файл → подмена), прежняя версия уезжает в `.bak`, нечитаемый файл — в `.corrupt`. **Easy Save 3 остаётся референсом, а не плановой заменой** (реш. 2026-07-26): мы сохраняем данные, а не объекты, поэтому сильные стороны ES3 (графы объектов, ссылки на `UnityEngine.Object`, полиморфизм) решают проблему, которой у нас нет.
- Сохраняем **данные, а не объекты сцены**. Отдельного DTO-слоя нет и он не нужен: `RunState` плоский, без SO-ссылок и рантайм-состояния, то есть **сам себе save-DTO**. Появится рантайм-поле — тогда и разделим. *(Прежде здесь значились `RunSaveData` и `UnitSaveData` — таких классов в коде никогда не было, имена из замысла; сверено 2026-07-26.)*
- **Сущности (юниты, реликвии, эффекты) хранятся по строковым ID** (`"relic_flame_sword"`), а **не** ссылками на ScriptableObject. SO — иммутабельные определения контента; в сейве на них ссылаемся по ID. Это переживает изменения ассетов и переносится между билдами/игроками.
- Под рогалик сейв компактен: при необходимости можно дополнить снапшот **сидом + логом команд** для точной воспроизводимости — см. [[tech/40-planning/seed|3. Рандомизация забега (Seed)]].
- **Версионирование схемы — ещё не работает.** Поле `RunState.SchemaVersion` пишется, но **никем не читается**, миграций нет. Пока это так, апдейт с изменением формата ломает старые сейвы молча: `JsonUtility` не жалуется на отсутствующие поля и разбирает чужой файл в наполовину пустой DTO с валидным видом. Целевой механизм (конверт, три исхода загрузки, цепочка миграций) — [[tech/40-planning/save-system|Planning - Save System]] §5–6. Тот же принцип нужен Workshop-UGC, см. [[tech/40-planning/steam-workshop|8. Steam Workshop и UGC]].
