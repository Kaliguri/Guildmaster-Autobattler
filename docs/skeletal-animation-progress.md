### 1.3 Разбор трёх клипов

**`Idle.anim` — фактически пустой.** 3.0 с, анимируются только позиции корней рук
(`Arm (Left)` / `Arm (Right)`, сдвиг 0.012 по Y), ключи 0 / 1.733 / 2.167 / 3.017. Первые два ключа
идентичны — 1.7 с полной статики. Корпус, голова, ноги не двигаются вовсе. Дыхание сейчас делает код
(`IdleBreath` — масштаб всего узла), а это пульсация, а не дыхание.
Побочно: Idle говорит на языке «позиция корня руки», а Run — «поворот Rotation Point». Разные каналы
на одну кость; не ломается, но это два языка вместо одного.

**`Run.anim` — по стоп-кадрам это не бег.** 0.5 с, 5 ключей на кривую (0 / 0.125 / 0.25 / 0.375 / 0.5),
симметричная синусоида — маятник, а не цикл локомоции.

| Признак бега | Норма | У нас |
|---|---|---|
| Число ключевых поз | 4 на шаг (contact / down / passing / up) | 2 крайности + 3 нуля |
| Амплитуда бедра | +40° / −30° | ±15° |
| Сгиб голени при заносе | 60–90° | ±8° вокруг покоя |
| Наклон корпуса вперёд | 8–15° | 0° (±2° симметрично) |
| Вертикаль корпуса (bob) | 3–6 % роста | 0.012 при росте 1.7 = 0.7 % |
| Фаза полёта | две за цикл | нет, ноги не отрываются |
| Руки | локти ~90°, мах высокий | прямые, ±18° |

Плюс фаза bob: максимум высоты стоит на максимальном разведении ног. Для бега это допустимо
(момент полёта), но нет «down» — просадки сразу после приземления, а без неё нет веса.

**`Attack.anim` — тайминг хороший, чистота плохая.**

Лишние ключи — есть, не кажется:

- **6 кривых полностью константны** (36 мёртвых ключей): `Leg (Right)/Rotation Point` (euler + pos),
  `Leg (Left)/Rotation Point` (pos), `Leg (Left)/Rotation Point/Leg_Down`,
  `Leg (Right)/Rotation Point/Leg_Boots`, `Arm (Left)/Rotation Point/Arm_Down` (pos).
- **4 кривые с плато из 3-4 одинаковых ключей подряд**: `Arm (Left)/…/Arm_Down` (58.4 четырежды),
  `Shield` (−100 четырежды), `Leg (Left)/Rotation Point` (−2.208 четырежды — амплитуда 2° и та невидима),
  `Arm (Left)` (позиция).
- **45 из 65 `m_EditorCurves`** — константы (оси X/Y эйлера, Z позиции).

Содержательно: **левая рука со щитом умирает после t = 0.183** — щит уезжает в −100° и стоит там весь
клип. Хореография односторонняя, вторая половина тела не участвует.

Тангенсы (кривые):

- Разгон в контакт есть и он правильный: выход из hold −698 °/с, вход в удар −3958 °/с.
- **Нет follow-through**: на кадре контакта скорость падает в ноль мгновенно, перелёта и отката нет.
- **Возврат 0.55 → 1.167 идёт с нулевыми тангенсами на обоих концах** — 0.6 с вялого дрейфа. Это самая
  «ватная» часть клипа.
- `m_LoopTime = 1` на клипе атаки — неверно по смыслу (хвост скрабится кодом).

Оверлаппинг частично сделан (меч и предплечье отстают на 1-2 кадра, голова тоже) — это плюс.

### 1.4 Почему боевой префаб не готов к VFX и тинтам

`UnitView` знает про **один** `SpriteRenderer`. У скелетного юнита их **16**. Отсюда:

| Что | Работает на скелетнике |
|---|---|
| Тинт `SetTint` | только торс |
| Вспышка удара (`_FlashAmount`) | только торс — и материал `MAT_Sprite_HitFlash` стоит **только на нём**, остальные 15 частей на дефолтном спрайт-материале, там этого параметра просто нет |
| Голограмма смерти, контур каста | только торс |
| Альфа стелса | только торс |
| Y-сортировка | пишется в торс, **ломая внутренний порядок частей** |
| `DeathShatter` | колет торс 0.17 × 0.26, остальное тело исчезает щелчком |
| Силуэт для драга расстановки | торс |

Это не «недонастроен префаб» — это отсутствующий шов.

### 1.5 Ревизия порядка отрисовки (28.07, Unity закрыт)

Фактический `sortingOrder` в `UnitView_BoneStandart`:

| order | часть | материал |
|---:|---|---|
| 0 | Body | **HitFlash** |
| 1 | Leg_Top ×2 | default |
| 2 | Leg_Down ×2, **Sword** | default |
| 3 | Leg_Boots ×2 | default |
| 4 | Arm_Shoulder ×2 | default |
| 5 | Arm_Top ×2 | default |
| 6 | Arm_Down ×2 | default |
| 7 | Head | default |
| 8 | Shield | default |

**Что здесь замысел, а не дефект** (уточнил Макс 28.07): ноги перед телом — так и планировалось; меч
ниже головы и руки — тоже. Не трогаем.

**Настоящий дефект один: левая и правая конечность неотличимы** — обе руки 4/5/6, обе ноги 1/2/3.
Порядок между равными значениями не определён, дальняя конечность может лечь поверх ближней. Это
«открытый вопрос» из канона ГДД, и он не закрыт.

Причина: обе руки — инстансы одного `Arm.prefab` (внутри `Arm_Down` 6 / `Arm_Top` 5 /
`Arm_Shoulder` 4), обе ноги — одного `Leg.prefab`. Пока порядок живёт в префабе конечности, развести
левую и правую нечем.

**Правило (Макс, 28.07):** значения для левой и правой стороны задаются **раздельно**, зависят от
персонажа, дефолт — **правая сторона выше левой**. Редактор порядка из Ф1b это и обеспечивает:
значения раскладываются с корня, префабные перестают что-либо значить.

Отдельно: материал `HitFlash` только на торсе — остальные 15 частей физически не умеют вспыхивать.

### 2.1 Перестройка рига — что сделано 28.07

Риг был **плоским на всех уровнях**, и это не стиль, а потолок: `Leg_Top` / `Leg_Down` / `Leg_Boots`
висели сиблингами под одним `Rotation Point`, то есть колена не существовало. Замер: поворот голени
на 50° двигает стопу ровно на ноль. У рук по той же причине не было локтя, а `Head` и обе руки были
сиблингами `Body` — наклон корпуса не тянул верх тела.

Стало:

```
Hips                                  ← вертикаль бега (bob) живёт здесь
  Torso                               ← наклон корпуса, тянет голову и руки
    Body · Head
    Arm (L/R) / Rotation Point        ← плечо
      Arm_Shoulder · Arm_Top
      Elbow                           ← локоть
        Arm_Down → Shield / Sword
  Leg (L/R) / Rotation Point          ← бедро
    Leg_Top
    Knee                              ← колено
      Leg_Down
      Ankle                           ← голеностоп
        Leg_Boots
```

Точки суставов посчитаны по середине нахлёста соседних спрайтов; Макс правит их глазами.
Аватар пересобран (он описывает иерархию — старый описывал скелет, которого больше нет),
`Mask_Arms` перепрописана на новые пути. Имена суставов без суффикса стороны: сторона уже в пути,
а канон требует одинаковых имён костей у всех ригов одного типа.

**Замеренные знаки** (гадать не надо, всё промерено координатой конечной точки):

| Кость | Знак | Смысл |
|---|---|---|
| Бедро (`Rotation Point`) | **+Z** | нога вперёд |
| Колено (`Knee`) | **−Z** | сгиб (пятка назад) |
| Корпус (`Torso`) | **−Z** | наклон вперёд |

**Клипы:**

- `Attack` **ретаргечен, а не перерисован** — хореография Макса цела. Повороты сегментов переехали на
  суставы, позиционные кривые потеряли смещение нового родителя. Заодно ушли **36 кривых плоских осей**
  и **8 мёртвых констант**.
- `Run` пересобран на суставах: колено гнётся до **60°**. Дальше — предел **арта**, не рига:
  прямоугольные сегменты без круглого шарнира расходятся щелью.
- `Idle` — цикл дыхания на 2.4 с вместо 1.7 с статики и твича рук.

**Боевой префаб был ФОРКОМ рига** — распакованной копией, а не инстансом. То есть правки скелета в бой
не попадали вообще, и два владельца одной структуры расходились молча. Теперь это настоящий инстанс.

**Готча, стоившая двух заходов:** `EditorUtility.CopySerialized` переносит и **имя** — клипы остались
безымянными, пока не вернули руками.

### 2.2 Риг-API — постановка и Ф0 (28.07)

Постановка Макса: крутить части тела было **непонятно и на костылях**. Углы клинка считались как
«куда он должен смотреть в мире минус вклад плеча и локтя» — каждый раз заново и в голове, поэтому
атаки 2 и 3 ломались трижды подряд. Решение — инструмент, который говорит на языке рига, и правила,
которые не надо держать в памяти.

**Опора, которую дала правка Макса.** Точка вращения предмета названа явно, а калибровочный оффсет
положен в **спрайтовый** дочерний узел (`Sword` = −89.39°), поэтому анимируемый узел остаётся чистым
нулём: при нуле клинок стоит под прямым углом к предплечью (замер — **90.61°**). Это единственный
узел рига, где ноль что-то значит; у остальных «стойка» размазана по анимируемым узлам (плечо 10°,
предплечье 26.61°, бедро 22.12°) — решение Макса оставить её там и работать **в дельтах от покоя**.

**Что выяснил ресёрч** (сузило объём работы):

- Все восемь клипов уже пишут `localEulerAnglesRaw` — это режим Unity **«Euler Angles»**, который
  держит полный диапазон: «если поворот больше 360°, объект провернётся целиком». Режим `Quaternion`
  наоборот всегда идёт коротким путём и физически не умеет больше 180°. Значит дуга на 200° законна —
  достаточно **писать углы непрерывным рядом и не нормализовать их в ±180**.
- У задачи есть индустриальное имя — **Euler filter** (Maya, Blender): проход по ключам, выбирающий
  для каждого ту из эквивалентных записей угла (±360k), которая сохраняет непрерывность ряда, не меняя
  самих поворотов. Изобретать «систему обхода дуг» не нужно.
- **Spine решает так же:** в режиме анимации локальный угол кости выходит за 0–360, и именно это
  задаёт направление и число оборотов; мировые оси там ограничены 0–360, поэтому работать надо в
  локальных.
- **«По часовой» — не инвариант.** `UnitView` разворачивает скелет через `scale.x = −1` на
  facing-root, а при отрицательном скейле те же +30° крутят клинок в другую сторону экрана. Сторона
  дуги задаётся как «через верх / через низ», а «по часовой» считается с поправкой на разворот.

**Ф0 — миграция имён (сделано).** Шарниры переведены в схему Макса
`Rotation Point (Shoulder / Elbow / Grip / Hip / Knee / Ankle)`: имя однозначно в Hierarchy, а то, что
в скобках, работает логическим id для API. Раньше четыре разных узла звались просто `Rotation Point`,
а хват слева и справа — по-разному (`Hand` против `Rotation Point (Item in Hand)`).

Сделал `RigMigrate` — переименование узла тянет за собой все ссылки-пути: биндинги клипов, записи
масок, пересборку аватара. Прогон: **12 узлов, 201 биндинг, 52 записи масок, 19 битых путей → 0.**

> **Готча, стоившая четырёх клипов.** Переименование узла в Hierarchy **молча** рвёт всё, что ссылается
> путём: кривая с мёртвым путём просто перестаёт анимировать, запись маски игнорируется, аватар
> описывает скелет, которого больше нет. Ни одной строки в консоли. Так `Attack`, `Attack2`, `Attack3`
> и `AttackCharge` потеряли меч (15 биндингов), а обе маски — по 2 записи. Переименовывать узлы рига
> только через `RigMigrate`.

**Что вскрылось, когда меч ожил.** Кривые клинка в четырёх атаках писались под **старый** ноль
(−66.4°) и старую точку хвата, поэтому их значения теперь смещены. Ход клинка после миграции:
`Attack` span 395° (суммарно 792°), `Attack2` 391°, `Attack3` 236°, `AttackCharge` 229°. Хореография
`Attack2` при этом читается верно (замах через низ за щит, рубящий снизу вверх, контакт на 7-м кадре) —
переписывать надо значения, а не замысел.

**Ф1 — профиль и разметка (сделано).** `RigProfile` — замер рига: id сустава → путь, поза покоя, ось
и длина кости, знак сгиба, лимит; для предметов — ориентир, калибровка, расстояния до рукояти и до
конца кости. Пересборка обновляет замеряемое и **сохраняет авторское** (знак сгиба, лимит) — это
анатомия, а не геометрия. Лимиты: колено 60° (предел арта из 2.1), локоть 120° и бедро 45° — оценка
Никси «дальше почти наверняка ошибка», валидатор только предупреждает.

`RigProbe` рисует невидимую половину поверх рендера: суставы, оси костей, хват, ориентир предмета и
куда он смотрел бы при нуле хвата. Первым же запуском поймал свою ошибку — клинок был нарисован в
обратную сторону из-за лишнего `−90` в формуле.

> **Готча замера:** «конец кости = следующий сустав» неверно. Следующий узел вниз по руке — хват, а он
> стоит в пивоте предплечья, поэтому локтевая кость мерилась как **0.0024**. Хват — точка крепления
> внутри кисти, из цепочки исключён; кости без сустава ниже мерятся до дальнего края спрайта (0.0790).

**Ф2 — авторинг по смыслу (сделано).** `RigWriter`: `Bend` — градусы от покоя в ту сторону, куда сустав
реально сгибается; `Aim` — **мировой** угол клинка с вычитанием цепочки и калибровки; `Arc` — какой
стороной идёт дуга; `Sweep` — плюс целые обороты.

Замеры на риге: `Shortest` и `Cw` идут коротким путём **160°**, `Ccw` — длинным **200°**, один лишний
оборот даёт **560°**, и все варианты приходят ровно в заказанные −25°. Это закрывает провал прошлого
захода, где рубящий снизу вышел на 19° вместо 200°.

> **Две ловушки порядка, найденные проверкой, а не рассуждением.** (1) Кривая держит значение первого
> ключа **назад во времени**: одинокий ключ на 0.8 с сгибает сустав с нулевого кадра. Теперь каждый
> анимируемый трек получает ключ покоя в t=0. (2) Цель нельзя решать в момент вызова — более поздний
> `Bend` выше по цепочке уводит клинок (замер: 40° на локте сдвинули цель на **25°**). Аимы решаются в
> `Write`, после засева и явных значений. Засев **после** решения аимов — своя же ошибка на **40°**.

`Write` проверяет себя: сэмплит готовый клип на каждой цели и предупреждает, если клип играет не то,
что заказано. `RigEulerFilter` — то же правило непрерывности для чужих кривых: `170` затем `−170`
гонит клинок 340° назад, после фильтра `170`/`190` и честные 20° вперёд. **Восстановить намеренную
длинную дугу он не может** — после нормализации намерение потеряно, дугу надо переавторить.

**Ф3 — валидатор (сделано).** Первый прогон по восьми клипам: **1 ошибка, 4 предупреждения**.

| Находка | Что это |
|---|---|
| `Attack` крутит меч **позиционной** кривой на спрайте меча | старая пре-грип разводка, ровно причина отрыва клинка |
| `Attack` / `Attack2` / `Attack3` / `AttackCharge`: скачки −194°, 205°, −226°, −203° | длинные дуги; в Euler-режиме играются как есть, но должны быть подтверждены явно |
| Щит: лицо в 140° от кости при нуле | ноль щита не значил ничего (исправлено в Ф4) |

Проверяет также мёртвые пути, смешанные типы rotation-биндингов, кривые не на всех осях и лимиты по
кадрам. **Сообщает, но не правит** — поза принадлежит автору.

**Ф4 — щит (сделано, решение Макса).** Ноль щита теперь значит «держу ровно»: верх щита стоит в
мировых **90°**, калибровка спрайта −40 → **−24.76**, поза в стойке повернулась на 15.24°. Ориентир
назван `top`, а не `face`: у плоского 2D-щита лицо всегда к камере, наклон задаёт верх.

### 2.3 Все восемь клипов переписаны на риг-API (28.07)

Рецепты живут кодом — `Rig/BoneUnitClipRecipes.cs`, меню `Alebardium/Animation/Rebuild Bone Unit Clips`.
Каждый клип читается как хореография, а не как сорок ключей. **Владение:** рецепт — первая версия под
приёмку; как только Макс правит клип руками, владельцем становится клип, и перезапуск рецепта затрёт
его работу. Перезапускать осознанно и поштучно.

**Тайминг-скелет атак** снят с эталона Макса (`Attack`) и сохранён: замах ~10 кадров → **hold крайней
позы 8–10** → удар 5–7 → **hold контакта 6–7** → долгое досаживание. Оверлаппинг тоже его: корпус
ведёт, голова и локоть отстают на кадр, кисть на два.

**График скорости** теперь задаётся явно (`Ease`): `EaseOut` — влетел и встал (контакт), `EaseIn` —
сорвался с паузы, `Linear` — без торможения в середине маха, `Hold` — плато. До этого все тангенсы
сглаживались, и «медленно вышел, разогнался, резко встал» задать было нечем.

| Клип | Что изменилось |
|---|---|
| `Attack` | тайминг Макса кадр в кадр; **исправлена конечная поза** — клинок дорубает вперёд-вниз (−70°) через переднюю полусферу (245°), а не уходит поперёк корпуса, как раньше |
| `Attack2` | восходящий через низ (205°), замах-присед, сила от разгибания ног, подъём таза 0.008 → 0.035 |
| `Attack3` | диагональный, 180° через переднюю полусферу, приходит в −50° (вертикальный — в −70°), чтобы удары читались как разные |
| `AttackCharge` | кадр ноль = поза спринта (вход только из бега), клинок выше (120°), удар 185° с наклоном корпуса −22° |
| `Block` | щит встаёт за 7 кадров (гвардия не «выезжает»), hold, лёгкое оседание; пишет только руку со щитом |
| `Idle` | дыхание: вдох 1.1 с, выдох 1.5 с (асимметрия — то, что не даёт лупу читаться механикой), таз 0.020 → 0.026, голова с лагом 2 кадра |
| `Walk` | добавлен вертикальный bob (таз ниже на контакте, выше на проносе) — без него шаг читался скольжением; руки тихие |
| `Sprint` | тот же четырёхпозный каркас, шаг и наклон больше, bob вдвое; одинаковое число шагов и фаза с `Walk`, чтобы бленд не дёргал ноги |

**Валидатор после переписывания: 0 ошибок, 0 предупреждений** (было 1 и 4). Маркеры контакта сохранены
(`Attack` 0.450, `Attack2` 0.380, `Attack3` 0.360, `AttackCharge` 0.467) — их читает боевой код.

> **Две ловушки, найденные глазами, а не отчётом.** (1) `Arc` применялся к ЛОКАЛЬНОМУ углу хвата, а
> автор думает в мировой дуге клинка: кисть шла коротким путём −26°, мировые 138° набирало плечо, и
> «против часовой» на локальном числе означало лишний оборот на экране. (2) Решение в абсолютных
> значениях дало эквивалент, сдвинутый на 360 (замер: 333.8 там, где нужно −26.2) — конечная поза
> совпадала, но кисть проворачивалась целиком. Лечение: считать в **дельтах** — сколько мира должен
> пройти клинок минус сколько даёт цепочка.

Порог самопроверки аимов поднят с 0.5° до 8°: расхождение в несколько градусов на плато — это работа
оверлаппинга (кисть отстаёт от плеча), а не промах, и шум заглушал настоящие ошибки.

**Мах должен быть ОДНИМ разгоном** (правка по замечанию Макса «атака 1 будто лагает»). Промежуточные
ключи между hold и контактом делят дугу на два ускорения, и клинок спотыкается посередине. Замер
скорости клинка по кадрам, до и после:

| Клип | Было | Стало |
|---|---|---|
| `Attack` | 49 → **25** → 46 | 36 → 49 → **55** → 54 → 38 → 13 |
| `Attack3` | 33 → 28 → **24** → 35 | 29 → 33 → **35** → 34 → 18 |
| `AttackCharge` | 42 → 35 → **28** → 36 | 36 → 44 → **46** → 33 → 10 |

`Attack2` был чист изначально — там промежуточного ключа плеча не было. Ключ разгибания ног в нём
оставлен: это отдельный такт, который и даёт удару силу, а клинок при этом идёт непрерывно.

**Пауза = кадры, полностью идентичные** (замечание Макса, 28.07). Первый заход этого не давал: замер
показал **ноль полностью статичных кадров** в клипах, которые обязаны держать позу дважды. Три причины,
все исправлены:

1. **Плато копировало намерение, а не позу.** `Hold` дублировал ордер аима («клинок в мировые 175°»), а
   к концу паузы цепочка уже другая, и тот же мировой угол потребовал другого локального: ключи паузы
   вышли −26.22 и −48.84 вместо двух одинаковых. Теперь плато — отдельный вид ключа, который повторяет
   предыдущее значение буквально и ничего не пересчитывает.
2. **Пауза кончалась у каждой кости в своё время.** Лаг разносит ВХОД в позу (корпус, голова, кисть), и
   я продлевала каждому его собственные 10 кадров от его собственного времени — концы разъезжались на
   0.333 / 0.349 / 0.35, и в зазорах корпус уже ехал, пока кисть стояла. `HoldUntil(t)` замораживает
   риг до одного общего момента.
3. **Мороз накрывал только уже упомянутые кости.** Сустав, у которого ключ стоит только в контактной
   позе, всю паузу интерполировался от покоя — то есть ехал. `HoldUntil` проходит по всем суставам
   профиля, а не по тем, что автор успел назвать. Позиционные кривые (таз) тоже получили `Ease`: без
   этого сглаживание выгибало их к следующему ключу, и на «замершем» кадре всё тело ползло вверх.

4. **Вход в позу у позиционных кривых оставался сглаженным.** Тангенс последнего ключа перед паузой
   смотрел на следующий ключ ЗА паузой, поэтому кривая выгибалась над плато и возвращалась: таз ехал
   вверх-вниз в кадрах, которые были плоскими по всем углам. `HoldUntil` теперь пинит и его.

**Результат — паузы, которые действительно стоят:**

| Клип | Замах | Контакт |
|---|---|---|
| `Attack` | 7 кадров | 6 кадров |
| `Attack2` | 6 | 5 |
| `Attack3` | 7 | 6 |
| `AttackCharge` | 4 | 7 |
| `Block` | 12 (гвардия) | — |

`Idle` / `Walk` / `Sprint` статичных кадров не имеют, и это правильно: цикл не замирает.

Проверка `swing-stutter` добавлена в валидатор: он сэмплит угловую скорость предмета по кадрам и
сообщает провал скорости посреди маха. Просадка в самом конце не считается — это удар останавливается,
в чём и смысл.

### 2.35 Класс ошибок «не в ту сторону» — разобран до корня (28.07)

Макс за один заход поймал пять ошибок направления подряд и сказал прямо: «невероятно много». Это был не
разброс невнимательности, а **один класс ошибок с пятью проявлениями**. Все замерены, все закрыты, у
каждой теперь автопроверка. Держать этот список под рукой при любой работе с углами.

| # | Ошибка | Как проявлялась | Почему | Лечение и проверка |
|---|---|---|---|---|
| 1 | `Arc` применялся к **локальному** углу хвата | меч на втором кадре уходил вниз и делал лишний оборот | автор думает в мировой дуге клинка, а кисть шла коротким путём −26°, тогда как мировые 138° набирало плечо | развёртка дуги в **мире**; проверка `long-way-round` |
| 2 | Решение аима в **абсолютных** значениях | поза совпадала, но кисть проворачивалась целиком (замер: 333.8° там, где нужно −26.2°) | эквивалентный угол ±360k тоже «совпадает» | считать в **дельтах**: сколько мира должен пройти предмет минус сколько даёт цепечка |
| 3 | Вклад цепочки через `Mathf.DeltaAngle` | клинок проходил **555°** вместо заказанных 245° | `DeltaAngle` складывает всё больше 180° назад в диапазон: путь плеча −194° читался как +166°, и кисть докручивала фантомные 360° | `ChainTravel` — интеграл поворота цепочки по кадрам |
| 4 | Сустав шёл коротким путём, а короткий был **неверным** | плечо на ударе уходило назад через 180° над головой | от 168° до −26° короткий путь = +166°, нужный = −194°; `Shortest` по умолчанию | сторона задаётся явно (`Arc.Cw`); проверка `long-way-round` предупреждает при пути близком к 180° |
| 5 | Значения суставов взяты из старых клипов **без проверки анатомии** | локоть выгибался наизнанку (угол между костями шёл +30 → +6 → −7 → −41 → −44) | никто не мерил, гнётся ли шарнир в эту сторону вообще | проверка `hinge-inverted`, отсчёт **от позы покоя рига**, а не от нуля |

**Родственный класс — «статика, которая не статична»** (паузы). Тоже одна причина в четырёх видах:
плато копировало намерение вместо позы; плато кончалось у каждой кости в своё время; заморозка не
накрывала кости, упомянутые только позже; позиционные кривые сглаживались через плато. Проверка —
замер полностью идентичных кадров (см. 2.3).

**Что проверить в остальном коде проекта тем же взглядом** (не сделано, кандидаты на отдельный заход):

- любой `Mathf.DeltaAngle` / `Mathf.LerpAngle` там, где важен **путь**, а не конечная ориентация: разворот
  юнита, доворот камеры, вращение снарядов и подсказок прицела;
- любое сравнение углов на равенство или на «меньше» без `DeltaAngle` (одна поза лежит и как −16.34, и
  как 343.66);
- нормализация угла в ±180 на выходе функции, чей результат потом интерполируется — это стирает намерение
  длинной дуги;
- места, где визуальное направление зависит от флипа (`scale.x = −1` на facing-root): «по часовой» там
  не инвариант;
- кривые, которые пишутся не целиком по осям (наша готча `anim-curve-axes-all-or-nothing`), и тангенсы,
  оставленные сглаженными там, где нужна остановка.

### 2.4 Замечания Макса к первой версии клипов (28.07) — ЖДУТ работы

Записано с его слов, решения за ним. Порядок — его приоритет.

**1. Щит используется слишком слабо.** По логике боя он должен прикрывать почти везде, кроме `Idle`:
быть «на подготовке», хотя бы легонько закрывать корпус. `Block` — это **активное** блокирование и
защита себя, а не поднятая рука. В атаках юнит раскрывается — и как раз поэтому должен по анимации
пытаться защищаться активнее. Всё это обязано сходиться с клипом блока (он живёт на слое с маской
`Mask_ShieldArm` над той же рукой).

**2. Гизмо слеша — прежде чем реализовывать взмах.** Нижний удар (`Attack2`) вызывает сомнения: странные
углы, странное начало и конец. Идея Макса: сначала построить **полный путь оружия** — где проходит клинок
от начала движения до конца, — посмотреть на него, и только если он читается, реализовывать клип. И
проверять так всегда. (Технически: свёртка позиции клинка по кадрам в одну линию поверх рендера; ближе
всего к этому `RigProbe` + onion skin, но пути оружия как отдельной кривой пока нет.)

**3. `Attack3` под вопросом как идея.** Диагональный удар в нашем 2D-ракурсе, похоже, не читается вообще.
Прежде чем доводить — решить, нужен ли он.

**4. Критерий приёмки — не «правильно», а «вах как красиво» и характер юнита.** Клип оценивается по тому,
как этот персонаж ДОЛЖЕН двигаться: рыцарь со щитом и мечом — тяжёлый, вязкий, защищающийся.

**Остаётся Максу на приёмку:** посмотреть в play-mode, где паузы длинные или короткие, и стоит ли
`Attack` возврат на 0.63 с (по рефам долгий recovery делает персонажа «липким», но у автобатлера он
заполняет интервал между ударами; на контактном листе видно, что больше половины клипа юнит стоит в
позе «меч внизу»).

### 2.5 Очередь доводки — решения Макса (28.07, вечер)

Замечания из 2.4 разобраны и превращены в очередь. Решения Макса, аргументы Никси помечены.

**Что вскрылось в обсуждении — я промахнулась по щиту тем же способом, что и по мечу:** мерила углы
вместо геометрии. Замер кадра контакта первой атаки:

| Что | В стойке | В атаке (контакт) | В блоке |
|---|---|---|---|
| `shoulder.L` от покоя | 0° | **+3°** | +33° |
| `elbow.L` от покоя | 0° | +13° | −27° |
| Наклон щита (мировой) | 90° (верх вертикален) | **50°** | 118–122° |

В момент максимального раскрытия левая рука стоит там же, где в стойке, а щит завален вниз-вперёд на
40°. «Прикрывает корпус» — вопрос не про угол, а про то, **перекрывает ли силуэт щита торс на картинке**.
Ровно как «читается ли взмах» — про путь клинка, а не про пару углов. Отсюда и порядок.

**Факт, который надо держать в голове: клип `Block` в игре не играется вообще.** Слой `Block` — Override
с маской `Mask_ShieldArm`, вес по умолчанию 0, `SetLayerWeight` не вызывается нигде в проекте
(`UnitView` играет только слой 0). Плюс в `Walk` / `Sprint` щит не пишется совсем — на бегу к врагу он
болтается в стойке, хотя по логике боя должен быть впереди.

Готча для поз: блендинг слоёв Animator идёт по кватернионам — коротким путём и без дуг больше 180°.
Значит поза «на подготовке» и поза блока обязаны быть **близки**, иначе на вкручивании веса рука поедет
через полкадра. Это аргумент за одну базу, от которой всё отклоняется.

| # | Что | Решение |
|---|---|---|
| A | **Гизмо слеша и силуэта** — путь оружия и перекрытие щитом, картинкой и числами | принято первым: инструмент приёмки для всех четырёх замечаний, без него авторинг снова идёт на глаз |
| B | **`Attack3`** | диагональ **отклонена** — в 2D не читается. Вместо неё **вторая вариация удара сверху**: отличимая от первой, но не радикально — именно вариация существующей атаки, а не третий почерк |
| C | **Щит как система** | `GuardReady` — **константа в `BoneUnitClipRecipes`**: каждый боевой клип стартует с неё для левой руки, `Idle` её не берёт, `Block` усиливает. Один владелец, правится одной строкой |
| D | **`Attack2` переавторить** по гизмо | после A: сначала путь, потом клип |
| E | **Проводка слоя блока** в `UnitView` | делается **в этом заходе**: `SetLayerWeight` через LitMotion 0→1 за 0.15 с, удержание, 1→0 за 0.3 с; поднятие предикцией на старте замаха атакующего (см. Ф4). Иначе блок нечем принимать глазами |
| F | Долги | колено спринта 15° за прямую, длина возврата `Attack` 0.63 с — не блокируют |

**Что показало гизмо на первых трёх атаках (28.07, замер).**

| Клип | Дуга удара | Удар длится | Контакт | Щит закрывает тело на контакте |
|---|---|---|---|---|
| `Attack` | 237° | 0.339–0.444 с | 0.450 с — **позже конца удара** | 9 % (макс 27 % на замахе) |
| `Attack2` | 190° | 0.306–0.378 с | 0.380 с, **в верхней точке дуги** | 1 % |
| `Attack3` | 177° | 0.289–0.383 с | 0.360 с, почти горизонтальный тычок | 1 % |

Плюс `Attack2` ведёт клинок **сквозь собственные ноги и землю**.

**Решения Макса по итогу замера:**

1. **Широкая дуга остаётся и приветствуется** — размах и есть линия, по которой потом рисуются слеш-трейл
   и свечение в духе SAO для активных способностей. Узкий удар нечем украшать.
2. **Контакт приходится на уровень корпуса цели** и в пределах досягаемости — это становится проверкой,
   а не пожеланием: маркер вне корпусного коридора считается ошибкой клипа.

**Поправки Никси, принятые внутри этих решений** (ни одна не сужает дугу):

- дуга не идёт сквозь собственные ноги и землю — лечится подъёмом плоскости и выносом клинка наружу;
- удар растягивается с ~0.10 до 0.13–0.15 с: 237° за три-четыре кадра размажут трейл в сплошное кольцо,
  и обещанное сияние станет нимбом, а не слешем. Вес добирается паузой перед ударом и жёсткой остановкой
  после, а не сужением размаха;
- маркер контакта ставится в ту точку широкой дуги, где клинок проходит корпусную высоту.

### 2.6 Отказ от сдвига костей — решение Макса (28.07, вечер)

**Целые позы на целых ключах.** Кости приходили в позу с разбегом в 1-2 кадра: корпус и плечо, следом
голова и локоть, последней кисть с клинком. На бумаге это оверлаппинг, на деле при 60 fps и таком
простом риге читалось **как лаг, а не как вес** — и делало фидбек неоднозначным: «поза кривая» не
говорило, какой из трёх ключей чинить. Убрано во всех восьми клипах, константа кадра-задержки удалена.

Оговорка Никси, принятая как «позже»: оверлаппинг сам по себе рабочий приём, но живёт он на **долгом
возврате**, где движение успевает прочитаться как след. Вернуть точечно и только в settle — после того,
как база принята.

**Побочный эффект, который это вскрыло.** Слияние ключей сдвинуло приход клинка раньше, и стало видно,
что у трёх атак из четырёх **маркер контакта стоял за концом удара**. Маркеры переставлены по замеру —
в самый быстрый сэмпл внутри ударной фазы, где кончик клинка пересекает корпусную полосу:

| Клип | Было | Стало | Кончик на контакте | Скорость |
|---|---|---|---|---|
| `Attack` | 0.450 | **0.400** | y 0.04, x 0.61 | 21.7 u/s |
| `Attack2` | 0.380 | **0.350** | y 0.05, x 0.64 | 29.7 u/s |
| `Attack3` | — | **0.400** | y 0.03, x 0.56 | 12.6 u/s |
| `AttackCharge` | 0.467 | **0.417** | y 0.09, x 0.49 | 26.5 u/s |

### 2.7 Заход 29.07 — гизмо, ручной проход Макса, круглая дуга

**Построено гизмо слеша** (`Rig/RigSweep.cs`, рисовалка вынесена в `Rig/RigCanvas.cs`): клип
сэмплится плотно, делится на замах / удар / возврат по скорости кончика, каждая фаза заливается
своей зоной — красная только у удара. Плюс числа, которых глаз не даёт: длина дуги, поворот клинка,
пик скорости, доля силуэта тела, реально закрытая щитом (пиксельное пересечение силуэтов, не угол).

**Что гизмо вскрыло сразу:** контакт у трёх атак из четырёх стоял ЗА концом удара; восходящий вёл
клинок сквозь собственные ноги и землю (кончик −0.44 при ступнях −0.336); щит на контакте закрывал
1–9% тела; диагональ (`Attack3`) читалась как горизонтальный тычок — по вердикту Макса заменена
второй вариацией удара сверху.

**Ручной проход Макса (`8e555182`).** Правил только меч и время, тело не тронул ни на градус:
единая сетка (замах 0.25 → пауза 0.333 → удар 0.583 → пауза 0.667 → возврат), удар растянут с ~0.1
до 0.21 с, и **кисть доворачивает в конце каждого удара** (`Grip.R` на 18–61° дальше). Пронос
вернулся, не нарушая правило двух ключей. Пики упали вдвое (22 → 13 u/s), дуги выросли до 257–285°.
Перенесено в рецепты (`5495ce0f`) — иначе прогон рецепта стёр бы работу.

**Баг возврата.** Плечо приходит в конец удара на скорости −776°/с; автоматический тангенс Unity
после перетаскивания ключей считался по соседям (−580°/с), кривая ныряла до −71° мимо стойки и
возвращалась. В рецептах на этом ключе `Ease.Out` — тангенс нулевой. Перелёт после переноса: 0.0°.

**Круглая дуга (`2e2ebfeb`) — главное открытие захода.** Зона удара рисовала спираль с вмятиной, а
не круг. Причина: клинок докручивал ПОВЕРХ руки — угол между клинком и предплечьем плыл с +11° до
−49°, радиус кончика от плеча рос на 30% за удар. Два вращения с разной скоростью дают эпициклоиду.
Круг получается только при постоянном угле клинок↔предплечье (жёсткий рычаг), а низкий финиш надо
покупать **наклоном корпуса** (он опускает плечо вместе со всей окружностью), а не кистью. После
правки нисходящего: разброс радиуса 3%, цена — дуга короче на 40° и кончик выше на 0.12.

**Осталось из этого захода:** раскатать круглую дугу на `Attack2` / `Attack3` / `AttackCharge` и
подобрать глубину финиша; рекавери восходящего (Макс назвал некрасивым); долги валидатора — локоть
`Block` −27° и колено `Sprint` 15°.

### 2.8 Шов тела — сделано 29.07 (шаг 6 порядка работ)

`IUnitBodyVisual` введён, обе реализации живут одновременно, `UnitView` больше не знает, из чего сделано
тело. Что оказалось важным по ходу:

- **Вспышки не было ни на одной части, а не «только на торсе».** Все 16 частей костяного префаба сидели
  на дефолтном URP-материале спрайта; `MAT_Sprite_HitFlash` встречался в проекте ровно один раз — в
  покадровом `UnitView.prefab`. То есть на скелетном юните не работал весь материальный слой целиком:
  вспышка удара, голограмма развоплощения, контур каста, прозрачность инвиза. Код честно считал числа,
  рисовать их было нечем. Материал разложен на все части.
- **Состояние тела за кадр подаётся ОДНИМ куском** (`BodyVisualState`), а не четырьмя вызовами: у
  составного тела получателей шестнадцать, и каждый параметр по отдельности означал бы шестнадцать
  записей property block на параметр. Повтор того же состояния не пишется вовсе.
- **Порядок частей переехал из `m_SortingOrder` в список на компоненте** (Ф1b). Переезд — стабильной
  сортировкой по текущему ордеру: у парных конечностей ордер одинаковый (по 2-3 части на значение), и
  обычный `Sort` перетасовал бы левую с правой. Текущая раскладка сверху вниз: `Shield`, `Head`,
  `Arm_Down` ×2, `Arm_Top` ×2, `Arm_Shoulder` ×2, `Leg_Boots` ×2, `Sword` + `Leg_Down` ×2,
  `Leg_Top` ×2, `Body`.
- **Разворот тела остался знаком масштаба корня** — `flipX` на каждой части отразил бы части по
  отдельности, не поменяв их взаимного расположения.
- **`Matrix4x4.lossyScale` теряет знак зеркала** (возвращает длины осей). Силуэт для drag-призрака
  хранит позы матрицами, и раскладывать их через `rotation`/`lossyScale` нельзя: у всей вражьей команды
  призрак смотрел бы в обратную сторону. Знак берётся из определителя (`SilhouettePart.Decompose`).
- **Найденный по дороге тихий баг:** вид, переиспользованный после чьей-то смерти, оставался с
  выключенным телом — второй жилец выходил на арену невидимым. Теперь `SetVisible(true)` на привязке.
- **Дуэль перестала занимать игровой контент.** `gm_spawn_bone_duel` спавнит `enemy.bone_dev` — свой
  ассет со ссылкой на костяной вид (урон 40, скорость атаки 0.8, остальное от класса). Раньше костяной
  вид вписывался руками в `relic.base`, и пока подмена стояла, костяным становился каждый бой базовой
  реликвии.
- Карточка пик-выбора красила тело через один `SpriteRenderer` — на скелетном герое покрасился бы один
  кусок. Теперь спрашивает у тела все части (рефлексией: UI-сборка намеренно не ссылается на
  Presentation).

**Осталось от шва:** ничего блокирующего. Порядок частей и глубина `Sword` относительно рук — на глаз
Макса в инспекторе (кнопки «Взять порядок из спрайтов» / «Применить порядок» на месте).

### 2.9 Проводка — заход 29.07 (шаг 7, начат)

Идёт со стороны, не занятой параллельным заходом: `UnitView` правит лента снимков, поэтому берём
симуляцию и контроллер.

- **Спринт живёт в симуляции** (Ф5 п.1-2): `RuntimeUnit.IsSprinting`, ставит и гасит `MovementSystem`.
  Порог — **зазор сверх собственной досягаемости**, а не сырая дистанция: «дальше трёх метров» для мили
  начало разбега, а для стрелка с досягаемостью 8 — уже позиция для стрельбы, и он бежал бы всегда.
  Числа в `SimTuningConfig`: ×1.3, вход при зазоре 1.0, выход при 0.3 (полоса — гистерезис). Разбега
  нет в кайте, отступлении, замахе и хвосте; флаг гаснет на смерти, контроле, полёте и потере цели.
- **Замер (энкаунтер-бенч, до/после).** Проходимость не изменилась нигде. Бои короче на 0.5-3.5 %.
  Цена в HP выросла в разбросанных составах: `DummyScatter` +12.5 %, `DummyTrio` +9.7 %, остальные в
  пределах ±3 %. Причина понятна: отряд быстрее собирается в свалку и меньше времени разменивается
  по одному. **Ждёт вердикта Макса** — принять как есть или сбавить множитель до 1.15-1.2.
- **Боевой контроллер собран.** Было три стейта (`Idle`/`Run`/`Attack`) при том, что `Sprint`,
  `Attack2`, `AttackCharge` и `Block` лежали на диске недостижимыми ассетами — отсюда «не работает ни
  разбег, ни щит»: играть их было нечем. Теперь слой 0 несёт шесть стейтов, плюс два слоя-надстройки
  весом 0 под код: `Arms` (маска рук) и `Block` (маска руки со щитом, клип `Block`).

- **Атака с разбега** (Ф6): прибытие разбегом взводит один свинг с собственным замахом
  (`UnitData.ChargeAttackWindupMult`, дефолт 1 — ни у кого тайминг не меняется), первый же удар его
  тратит. Заряд даёт только прибытие: разбег, оборванный смертью цели или контролем, не даёт ничего, а
  новое сближение гасит старый заряд. Длина считается в `AttackTiming.WindupTicksFor`, а не при входе в
  замах, — иначе гейт атаки предсказывал бы попадание по одной длине, а свинг шёл бы по другой.
  Дев-бойцу выставлено 1.5 под смотр.

- **Замах скелетных юнитов был 3 тика (0.10 с) — найдено 29.07.** Сим выводит замах из кадров клипа
  (кадр контакта ÷ число кадров), а у скелетного рига кадров нет вовсе: расчёт давал ноль и падал на
  телеграф-пол при интервале атаки 55 тиков. Клип (~0.58 с) скрабился в эту десятую долю секунды и летел
  примерно вшестеро быстрее задуманного — **это и есть главная причина «дёрганно и слишком быстро»**,
  ступеньки по тикам лишь вторая. Теперь `UnitData.WindupShare` задаёт долю прямо; у дев-Защитника
  замах 0.43 с, удар с разбега 0.27 с. Покадровые юниты не тронуты (доля 0 = старый путь), поэтому
  боевые тайминги игрового контента не поехали и бенч не нужен.
- **Множитель разбега развёрнут: 0.6 вместо 1.5.** Решение Макса: раз бег идёт с поднятым мечом, замах
  уже сделан бегом, и с разбега остаётся взмах — значит замах КОРОЧЕ обычного.

- **Проводка показа сделана** (когда `UnitView` освободился). Состояний анимации стало шесть: к
  `Idle/Run/Attack/Death` добавились `Sprint`, `AttackCharge`, `Stun`. Разбег и удар с разбега приходят
  ПРИЗНАКАМИ СИМУЛЯЦИИ через снимок ленты, а не угадываются по наблюдаемой скорости (за один тик
  прибавка 30% неотличима от толчка сепарации). Оглушение идёт от `CanAct` и старше атаки: сим замах при
  контроле рвёт, и показ не должен втиснуть удар, которого уже нет. Покадровые юниты не задеты —
  `Animator.Play` по несуществующему стейту это тихий no-op.
- **Клип `Stun`** (просьба Макса): меч и щит висят, колени подгибаются, корпус складывается, голова ведёт
  медленный круг в противофазе с руками. Гизмо поймало, что при −74° клинок проходит сквозь пол —
  поднят до −40°.
- **Три раза подряд готовый клип был недостижим** (спринт, разбег-атака, стан). Причина структурная:
  боевой контроллер и стенд синхронизировались руками, то есть список клипов был фактом с двумя
  владельцами, и проигрывал всегда стенд — тот, в котором смотрят. Теперь оба собираются из клипов на
  диске (`BoneUnitControllerBuilder`), пересборка рецептов тянет пересборку контроллеров. Слой щита
  называется **`Block`** (не `Brace` — имя из черновика плана было ошибкой).
- **Баг «удар в рывке не срабатывает».** Заряд разбега взводился и тратился ВНУТРИ одного тика (движение
  ставит при прибытии, авто-атака тем же тиком входит в замах), а снимок снимается ПОСЛЕ тика — показ
  читал всегда `false`. Разведено на два факта: `ChargedAttackReady` (миг в симе) и `ChargedSwing`
  (держится весь свинг, едет в снимке). Тест на регресс стоит.

**Правило показа (Макс, 29.07): подача — да, переписывание — нет.** Знание будущего даёт право решать,
_когда и как долго_ показывать момент, но не отменять события сима. Холостой замах показывается холостым:
«ого, он уклонился», «ого, успел убежать» — это события боя, и показ, вычищающий их, делает бой глаже и
беднее. Отсюда и потолок замысла «длинный эффектный замах»: тянуть подачу можно, врать о том, что
случилось, — нельзя.

**Телеграф «Оплота» — по-прежнему ЗАРАНЕЕ, но по знанию, а не по догадке.** Поза щита должна
подниматься за некоторое время ДО удара, иначе она не телеграф. Разница лишь в источнике: показ идёт с
лагом, поэтому в момент показа тика T режиссура читает события ленты за тиком T и ЗНАЕТ, что на тике
удара ляжет щит. Предикция (Ф4) как способ это узнать отменена — но сам подъём позы заранее остаётся
обязательным и делается в презентации, когда освободится `UnitView`.

**Предикция «Оплота» (Ф4) отменена — лента сделала её ненужной.** План писал предикцию как временную
меру до лага презентации и прямо оговаривал: с лагом «про срабатывание Оплота мы ЗНАЕМ, а не гадаем».
Лаг уже внедрён: в ленте есть `EffectApplied` с определением эффекта, и режиссура читает события, до
которых показ ещё не дошёл. Телеграф щита строится на ФАКТЕ будущего тика; писать предикцию значило бы
завести мёртвый код с собственным классом ошибок (щит поднялся впустую).

   | Слой | Маска | Содержимое | Вес |
   |---|---|---|---|
   | 0 Base | нет | `Idle` / `Run` / `Sprint` / `Attack1` / `Attack2` / `Death` | 1 |
   | 1 Arms | руки + дети | атака поверх бега — для части бестиария | 0↔1 кодом |
   | 2 Block | рука со щитом + щит | поза реакции | 0↔1 кодом |

   Слой 0 остаётся тем, что скрабит `UnitView` — код не переписывается.
4. **A4**: `WriteDefaults` = ON на всех стейтах слоя 0. Надстройки живут весом слоя, а не стейтом
   `Empty` — тогда готча с `writeDefaults` исчезает как класс.
5. **A5**: `SortingGroup` на корне визуала, `UnitView` пишет Y-sort в него (одна запись вместо 16).
6. **A9**: убрать `Attack_Original.anim` / `Attack_processed.anim` из `Assets/`.
7. **Ревизия наследия Cursor Auto.** Пройти всё, что пришло от него, а не только то, что бросается в
   глаза: `Arm.prefab` / `Leg.prefab` на расхождение иерархии с каноном имён костей, `BoneUnit_Combat`
   на мёртвые стейты (`Hit` и `Death` на `Idle.anim`, `m_DefaultWeight: 0`), клипы на константные
   кривые и `LoopTime`, префаб на дубли и потерянные ссылки. Итог — список правок, а не «вроде норм».

### Ф1 — шов тела (то, ради чего DI)

Ввести `IUnitBodyVisual` — «тело юнита» вместо голого `SpriteRenderer`:

```
SetTint(Color) · SetFlash(amount, color) · SetHolo(...) · SetOutline(...)
SetSortingOrder(int) · Bounds · CaptureSilhouette() · Hide() · SpawnShatter(...)
```

- `SpriteBodyVisual` — текущий одно-спрайтовый путь. **Фолбэк: если компонента нет, собирается из
  `_sprite` автоматически** → 17 существующих префабов не трогаем вообще.
- `SkeletalBodyVisual` — кэширует все `SpriteRenderer` под корнем, пишет `MaterialPropertyBlock` в
  каждый (без аллокаций), сортировку отдаёт `SortingGroup`, шаттер зовёт на каждую часть с общей
  палитрой и общим таймингом (тело разлетается по частям — это и выглядит лучше).
- Валидатор + editor-кнопка «поставить `MAT_Sprite_HitFlash` на все части».

Оба варианта живут одновременно, переключение — заменой компонента на префабе.

#### Ф1b — редактор порядка частей (просьба Макса 28.07)

Порядок отрисовки частей **перестаёт жить в `m_SortingOrder` каждого спрайта**. Владелец один —
`SkeletalBodyVisual` на корне: список частей сверху вниз, как слои в Photoshop.

- Инспектор: reorderable-список имён частей, перетаскивание меняет порядок, кнопка «Применить»
  раскладывает `sortingOrder` по индексу и помечает префаб грязным.
- Применение идёт **внутрь `SortingGroup`** — снаружи юнит остаётся одним объектом в Y-сортировке
  арены, внутри порядок наш.
- Кнопка «Собрать заново» пересканирует иерархию: новые части падают в конец списка, исчезнувшие
  вычищаются. Дубликатов и потерянных ссылок быть не может — список сверяется с деревом.
- Это ровно тот же владелец, что уже нужен для вспышки и тинта: одна сущность знает все части, а не
  три разных места.

### Ф2 — три клипа

1. **Маркер контакта (A6).** Явное поле `_attackClip` на `UnitView` как источник маркера, фолбэк на
   `UnitVisual`. Маркер — `AnimationEvent "Marker"` на кадре контакта (t ≈ 0.433).
2. **Калибровка бега (A8).** Перевести с «юнитов на кадр» на **«мировых юнитов за цикл клипа»**:
   `speed = v × clipLength / metersPerCycle`. Для покадровых юнитов старая формула остаётся.
3. **`Run.anim` — переписать.** 8 ключей (2 шага × 4 позы), бедро +40/−30, голень до 70° при заносе,
   корпус наклонён вперёд 8°, bob 3-4 % с просадкой на приземлении, руки согнуты. Тангенсы по фазам:
   торможение в крайних позах, разгон в отталкивание.
4. **`Idle.anim` — пересобрать.** 2.0–2.4 с луп: дыхание корпуса Y и поворот ±1°, голова с лагом 2 кадра,
   руки едут за корпусом (оверлаппинг). Редкий «твич» — отдельным клипом `Idle_Break` позже, не в лупе.
5. **`Attack.anim` — чистка и доводка.** Снести 6 мёртвых кривых и плато-ключи, сбросить `LoopTime`,
   оживить левую руку, добавить follow-through после контакта и переписать тангенсы возврата
   (быстрый уход из позы удара, медленное досаживание). Прогон через `AnimationLabProcessor`, сверка
   контактным листом до/после.

### Ф3 — вторая атака

- Стейты `Attack1` / `Attack2` в саб-машине, выбор варианта — **презентацией** (не из сим-RNG).
- Чередование с уклоном, а не чистый рандом: A, B, A, B с ~20 % шансом повторить.
- **Маркер читается из клипа конкретного варианта** — иначе при одном сим-тайминге удар придёт в разное
  время.
- Второй клип собирается из первого сменой траектории (удар сверху → диагональ снизу-вбок).

### Ф4 — поза блока = телеграф «Оплота» (решение Макса 28.07)

Блок перестаёт быть косметикой: он привязывается к реальной механике `BulwarkComponent` («Оплот»),
а текущий спрайт с щитом объявляется заготовкой под Защитника. Тестовый юнит — он же.

Клип-поза в 1-2 ключа + `SetLayerWeight` через LitMotion: 0→1 за 0.15 с, удержание, 1→0 за 0.3 с.

**Важная поправка к постановке.** «Оплот» **не просчитан заранее** — по коду это реактив в
`OnPreDamage`, щит встаёт в тот же тик, что и урон.

> **Куда это идёт в итоге.** Намерение Макса (28.07) — сим считает бой быстрее реального времени, а
> игроку показывается «мультик» с задержкой. Тогда про срабатывание «Оплота» мы **знаем**, а не гадаем,
> и тем же ходом решается давняя хотелка про slowmo, начинающийся чуть раньше смерти. Это отдельный шов
> (`UnitView` перестаёт читать живой `RuntimeUnit` и читает буфер снимков), он дорог в ретрофите и
> должен учитываться при любой правке презентации. Пока его нет — телеграф делаем предикцией и **не
> выдаём за знание**.

До лага презентации поза поднимается **предикцией на старте замаха атакующего**:

- предикция читает состояние сима и ничего в него не пишет — это законно;
- запрос: «есть ли готовый заряд у цели» + «выполнится ли триггер `PassiveTrigger`»;
- для `AnyHit`/`Always` предикция точна;
- для `OnHitAbovePctMaxHp` — считается по ожидаемому урону атакующего (авто-атака детерминирована),
  поэтому точна тоже, но остаётся уязвимой к тому, что между замахом и ударом цель успеет получить
  урон от третьего лица и порог сместится;
- если предикция ошиблась — щит поднялся впустую. Это читается как «приготовился, но не понадобилось»
  и ложью не является. Обратная ошибка (не подняли, а Оплот сработал) хуже, поэтому при сомнении
  поднимаем.

Замах короче 0.3 с → поднимаем сразу, без опоздания.

### Ф5 — спринт

1. **Ускорение +30 % — это симуляция, а не презентация.** Иначе анимация обгонит позицию. Значит
   модификатор скорости в симе при дальней цели → меняется время подхода → **нужен прогон бенча**.
2. **Триггер — дистанция, не время.** «Бежал 1 с» ломается на коротких перебежках и мигает. Вход при
   d > 3.0, выход при d < 2.0 (гистерезис).
3. **Blend Tree по `Speed`, а не второй стейт с переходом.** У двух циклов с разной длиной ноги
   «прыгают» на кроссфейде, если фазы не совпадают. Условие: у `Run` и `Sprint` одинаковое число шагов
   на цикл и совпадающие фазы — тогда бленд идеален.
4. **Наклон корпуса — кодом на корне** (глагол `LeanIntoRun`), масштабируется по скорости плавно и не
   требует второго набора клипов.
5. **Пыль — по маркерам шагов.** Сейчас `VfxContactDust` спавнится на старте/стопе движения. Нужны два
   маркера contact на цикл, презентер спавнит по ним.

### Ф6 — атака с разбега

Отдельный клип `Attack_Charge`, вход только из `Sprint`. Требует, чтобы сим знал: первый удар после
сближения имеет другой windup. Делать **не** «уникальную на юнита», а как вариант атаки с флагом
«требует разбег».

## Часть 3. Что ещё стоит заложить

Приоритет сверху вниз.

| Клип | Зачем | Слой |
|---|---|---|
| `Hit` | реакция на урон сейчас чисто кодовая (вспышка + сплющивание); клип даёт вес, не прерывая ноги | надстройка, маска корпус + голова |
| `Idle_Break` | редкая вариация простоя; с разным фазовым сдвигом оживляет толпу | слой 0, редкий переход |
| `Cast` / `Channel` | у нас уже есть контур каста, позы под него нет | слой 0 или надстройка |
| `Spawn` | появление на арене | слой 0 |
| `Victory` | у нас есть hold-frame в конце боя — победная поза дала бы кадр | слой 0 |
| `Idle_Combat` vs `Idle_Peace` | боевая стойка против расслабленной | слой 0 |

`Turn` и knockback-реакция отдельными клипами не нужны — они уже живут кодом на корне
(flip-squash, displacement), и это правильный слой для них.

Две поправки к исходной последовательности Макса:

- **Гигиена рига идёт ПЕРЕД клипами, а не после.** Она трогает маски, слои и `WriteDefaults` — то есть
  ровно то, к чему клипы привязаны. Настроить клипы, а потом перекроить слои — значит настраивать
  дважды.
- **Шаг 3 нельзя отложить до шва.** Без маркера контакта удар в бою приходит на последний кадр клипа,
  без калибровки «метров за цикл» бег крутится не в том темпе — новый `Run` попросту нечем выставить.
  Обе правки маленькие и к большому шву отношения не имеют.

Всё остальное — как сказал Макс: клипы раньше шва, проводка после.

## Решения Макса (28.07.2026)

1. **Блок → телеграф «Оплота».** Спрайт с щитом — заготовка под Защитника, тестируем на нём. Поза
   привязана к реальной механике, косметической ложью не будет. Оговорка про предикцию — в Ф4.
2. **Спринт: механика ускорения живёт в симуляции**, триггер по дистанции. Прогон бенча обязателен.
3. **Порядок: сначала чиним всё.** Ф0 + Ф1 идут первыми, до клипов. Отдельно ревизуем то, что пришло
   от Cursor Auto — доверия к нему нет.
4. **Порядок частей — редактором, а не полем на каждом спрайте.** См. Ф1b.
5. `Idle` пересобираем — согласовано.
