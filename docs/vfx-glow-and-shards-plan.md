# Свечение и осколки — заказ 2026-07-26

Пакет из шести правок боевого VFX по референсу SAO (скрины Макса от 2026-07-26) плюс
переработка маски арена-перехода. Рабочий журнал: сюда пишем вердикты, готчи и что сделано.
Смежное: [`arena-swap-progress.md`](arena-swap-progress.md), контур `xgaida-x-nixi-gamefeel-vfx`.

Статус: **разбор проведён, реализация не начата.**

---

## Корень: постобработки нет

`Assets/DefaultVolumeProfile.asset` → Bloom: `active: 1`, `threshold: 0.9`, **`intensity: 0`**.

Bloom формально в профиле, но выключен нулевой интенсивностью. HDR в URP включён
(`m_SupportsHDR: 1`), постобработка на камере WorldScene включена (`m_RenderPostProcessing: 1`) —
то есть весь тракт готов, не хватает одного числа.

Следствие: `ShatterEmberColor` (HDR) и `ShatterEmberBoost = 2` сейчас **не дают ничего** —
яркость выше единицы просто клампится на выводе. Пункты 1.3, 3, 4, 5 заказа без включённого
bloom физически нечитаемы: «яркий белый» и «glow-осколок» — это и есть постобработка.

**Вердикт: bloom включается первым, до всех остальных пунктов.** Порог держим ≥ 1.0, чтобы
светились ТОЛЬКО эффекты, а не пиксель-арт целиком; VFX выводим с яркостью 2–4.

## 1. Смерть юнита

### Что есть сейчас

`UnitView.OnDeath()` → `DriveDeath()`: ждём догорания hit-flash → анимация смерти →
anticipation (белый силуэт + дрожь, `_deathAnticipateDuration = 0.1`) → `DeathShatter.Play`.

`DeathShatter` + `ShatterMesh` + `SH_Sprite_Shatter`: видимая область спрайта режется на
блоки по пиксель-сетке, каждый летит как жёсткое целое (псевдо-3D кувыркание + спин + дрейф
вверх-и-наружу), цвет идёт тремя фазами — вспышка в белый → родной цвет → выцветание в
`_EmberColor`.

### Что менять (по пунктам заказа)

| # | Заказ | Где правится | Готча |
|---|---|---|---|
| 1a | Осколки **мельче** | `ShatterBlockPixels` 6 → 3 | **Кламп режет.** `ShatterMesh.Build` жёстко зажимает `cols ≤ 16`, `rows ≤ 20`. На спрайте 48 px и блоке 3 px нужно 16 колонок — упираемся ровно в потолок, дальше уменьшение параметра не даёт эффекта. Поднять клампы (до 48/64) заодно с параметром. |
| 1b | Осколков **больше** | следствие 1a (сетка гуще) + отдельный слой мелких искр | Число блоков растёт квадратично: 16×20 = 320 → 48×64 = 3072 квада. Это по-прежнему ОДИН дро-колл (весь меш в вершинах), но меш строится на каждую смерть — пиковая аллокация растёт. Держать потолок разумным. |
| 1c | Осколки **дольше живут** | `ShatterDuration` 0.75 → ~1.8–2.2 | Мало поднять число: сейчас альфа гаснет линейно (`1 - age`), и длинный разлёт превратится в долгое мутное угасание. Нужна кривая «держится ярким, гаснет в конце» (`pow(1-age, 0.35)`). |
| 1d | Дрейф в стиле рефа | шейдер: `md = t*t` → ease-**out** | Сейчас разлёт ускоряется (ease-in). В рефе осколки выстреливают резко и тормозят, продолжая тлеть. |
| 1e | Стадия **голограммы** | новая фаза в `DriveDeath` + параметр `_Holo` в `SH_Sprite_HitFlash` | Материал уже стоит на теле юнита и уже управляется через `MaterialPropertyBlock` — отдельный материал/рендерер не нужен. |
| 1f | Стадия **белого свечения** | `_deathAnticipateDuration` + HDR-цвет вспышки | Работает только после включения bloom (см. выше). |
| 1g | **Цвет** осколков | `_EmberColor` → рампа из трёх HDR-цветов + per-shard джиттер | См. ниже. |

### Стадии смерти после правки

```
обычный → [голограмма ~0.3с] → [белый пересвет ~0.15с] → [разлёт ~2с]
```

Голограмма: спрайт теряет насыщенность, становится полупрозрачным, набирает бирюзовый
контур (rim по альфе) и лёгкие скан-линии. Это ровно скрин 2 рефа и та фаза, которой у нас
сейчас нет вообще — сразу белеет и рассыпается.

### Цвет осколков — разбор рефа

На скринах видно, что это **не один цвет**, а рампа с разбросом:

- **ядро** — белый пересвет, почти без оттенка;
- **тело** — циан/бирюза (наш нынешний `_EmberColor` попадает сюда);
- **края** — глубокий синий, уходящий в индиго;
- **вкрапления** — часть осколков заметно уходит в жёлто-зелёное (салатовые искры в ядре
  вспышки), это не шум компрессии, оно есть на нескольких кадрах.

Значит вместо одного цвета — три HDR-цвета в конфиге (core / mid / tail), выборка по
возрасту осколка, плюс per-shard сдвиг оттенка в тёплую сторону для доли кусков (случайное
значение у осколка уже есть — `COLOR.a`, занят кувырканием; добавить второй набор в UV2/UV3).

### Смена блендинга

Осколок-«glow» в рефе — **аддитивный**: он светит поверх фона, а не заслоняет его. Наш
шейдер на `Blend SrcAlpha OneMinusSrcAlpha`. Предложение: переводить блендинг по возрасту
через premultiplied alpha (`Blend One OneMinusSrcAlpha`, rgb домножается на альфу) — тогда
ранняя фаза (кусок спрайта) остаётся обычной, а поздняя (тлеющий уголёк) светится.

## 2. Осколки от попадания

Заказ: при ударе от цели летят красно-белые осколки **в сторону удара**; чем больше урона —
тем больше осколков.

Есть: `VfxData VfxHitSpark` спавнится в `HitPoint`, сила удара влияет только на **масштаб**
(`EvaluateHitVfxIntensity` → множитель scale). Направление уже прокидывается — презентер
переопределяет `DefaultDirDeg`.

Менять: сила удара должна управлять **количеством** частиц, а не размером — толстая искра
читается как «крупный VFX», а частая — как «сильный удар». Нужен параметр burst-count на
`PooledVfx`, который презентер задаёт при спавне.

Открытый вопрос — цвет: красно-белый всегда, или по школе урона (у нас уже есть
`ResolveHitFlashColor` — физика/магия/яд/свет/тьма). См. вопросы внизу.

## 3. Свечение оружия под эффектом + радиальный всплеск

Самый архитектурно тяжёлый пункт, и самый ценный.

Сейчас статусы показывает `CombatStatusOverlay` — dev-кольца на Shapes, в собственной
доке помеченные как «не финальный VFX, инструмент наглядности».

Нужен шов **эффект → визуальная метка**: у `EffectData` появляется ссылка на `VfxData` +
сокет + режим (разовый/привязанный на время действия). Определение поля — стык с
`data-authoring`, спавн и жизненный цикл — мои.

Готча: **сокета оружия нет.** На `UnitView` есть Feet / Head / Shot / Hit. Пока тело юнита —
один спрайт, «светящийся клинок» буквально сделать нельзя: нечего подсвечивать отдельно.
Реалистичный путь — аура/трейл VFX-префабом на новом `WeaponPoint`, а настоящий emissive-клинок
приедет вместе со скелетной анимацией, где оружие станет отдельной костью и спрайтом.

Радиальный всплеск на активацию сильного — отдельный дешёвый VFX (кольцо, аддитив,
0.25–0.4с), не привязан к оружию и делается независимо.

## 4. Свечение слешей и снарядов

Слеш-VFX в проекте **нет вообще** (ни ассетов, ни кода) — это новый контент, а не правка.
Дуга по направлению атаки на `HitPoint`, аддитив, короткая (0.12–0.2с).

Снаряды: `ProjectileView` есть, нужен светящийся трейл и HDR-цвет тела. Опять же читается
только после bloom.

## 5. Огоньки на месте павших

Заказ: когда погибает наш персонаж, на его месте остаётся огонёк, цвет — от реликвии.

Готча: у `RelicData` **нет цвета** — только `DropRarity`. Нужно решить, откуда цвет:
поле в реликвии, палитра по редкости или палитра по тегу. Нужен и ответ на вопрос
«чья реликвия», если на юните их несколько.

Механика простая и шов готов: по `UnitDiedEvent` для юнита игрока спавним VFX-префаб в
`FeetPoint`, живёт до конца боя, гасится на `OnBattleReset`. Функция — информативность:
в кооп-хаосе видно, кто и где выбыл.

## 6. Бесформенная маска арена-перехода

Заказ: переход должен идти не по клеткам, а хаотичными бесформенными пятнами, «на весь
тайлмап целиком».

**Да, выполнимо, и почти вся нынешняя обвязка остаётся.** Ключ — развести две разные вещи:

- **физическая подмена тайла** обязана быть поклеточной — `Tilemap` не умеет половину тайла;
- **то, что видит игрок** (маска цифры и маска обесцвечивания) поклеточной быть НЕ обязана.

Решение: момент перещёлка берётся не из клеточной сетки, а из **шумового поля** —
fBm с domain warping (клякса, а не круг). Тайл физически меняется, когда его центр уже
накрыт цифровым слоем, — щелчок остаётся невидимым.

Единый источник правды сохраняем печью: шум считается **один раз на CPU** в текстуру,
шейдер сэмплирует ту же текстуру билинейно, C# читает её по пикселю. Формулу дублировать
в HLSL нельзя — на этом уже обжигались (целочисленный хеш вместо `sin`, потому что HLSL и C#
расходятся в младших разрядах).

Что меняется в коде:

1. Карта клеток разделяется надвое: **состояния** (пусто/пол/стена — клеточная, `Point`) и
   **моменты** (шумовое поле, разрешение ×4–×8 от клетки, `Bilinear`). Сейчас они упакованы
   в каналы одной текстуры — R состояние, B момент.
2. `ArenaSwapSchedule` перестаёт быть единственным владельцем ответа «когда»: момент теперь
   читается из поля. Хеш остаётся для мелкой вариации внутри пятна.
3. `SH_Arena_Digital` и `SH_Sprite_Desaturate` сэмплируют карту моментов билинейно — граница
   становится гладкой и рваной сама собой.
4. Контур («узнаваемые силуэты») продолжает считаться по карте состояний — он и должен быть
   по границам содержимого.

Готча: `linear: true` для карты моментов обязателен (см. журнал арены — sRGB прогоняет числа
через гамму).

## Открытые вопросы

1. Цвет осколков от попадания — красно-белый всегда или по школе урона?
2. Порог bloom — светятся только VFX (порог ≥ 1.0) или весь яркий арт слегка сияет?
3. Цвет огонька павшего — новое поле в реликвии, палитра по редкости или по тегу?
4. Голограмма перед смертью — только для гибели, или это общий язык «юнит уходит»
   (отступление, изгнание, призыв в обратную сторону)?
