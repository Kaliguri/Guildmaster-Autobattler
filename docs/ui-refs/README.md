# UI-референсы — рабочая база Никси

Назначение: **опора для анализа и дизайна наших экранов**. Не галерея «красивого»,
а рабочий инструмент, из которого я (Никси) читаю картинки и разборы, садясь чинить
конкретный экран.

## Почему это файлы в репо, а не «насмотренность»

Я не помню картинки между сессиями. Но я читаю файлы — включая PNG. Поэтому каждый
реф живёт здесь как **картинка + текстовый разбор**. Мудборд в голове бесполезен;
мудборд в `docs/ui-refs/` — рабочий. Садясь за экран награды, я открываю
`reward/` и опираюсь на разложенное, а не фантазирую.

## Разделение труда

- **Макс** — вкус и насмотренность; кладёт картинки в базу (или даёт ссылки).
  Визуальную приёмку держит он.
- **Никси** — структурирует, разбирает (teardown), раскладывает по полкам так, чтобы
  этим можно было пользоваться потом. Рефы «из головы» не тяну — это не арт-навык.

## Структура

```
docs/ui-refs/
  README.md              — этот файл: принципы, методика, источники
  _teardowns/            — разборы: <game>-<screen>.md (по шаблону _TEMPLATE.md)
  main-menu/             — главное меню, титул
  settings/              — настройки, аудио, управление
  shop/                  — магазин, торговец
  reward/                — награда после боя, выбор реликвии
  event/                 — текстовые события (StS-style)
  combat-hud/            — боевой HUD, полоски, таймлайн
  party-loadout/         — сбор отряда, расстановка, лут-грид
```

Каждый экранный тип соответствует нашему живому экрану (см.
`Assets/_Project/UI/Screens/`). Реф = `<game>__<screen>.png` + короткий `.md` рядом
(или строка в общем teardown).

## Эталоны вкуса (из скилла uitk)

- **Как надо:** **Balatro** (плотность + чёткие зоны + ховер-тултипы),
  **Hades** (HUD уведён в периферию, центр — игре).
- **Как НЕ надо:** **Slay the Spire** (перегруженный бой + слишком мелкий магазин).

Наш стек — **пиксель-арт** (шрифты VT323/bitcell, спрайты Honeti). Значит рядом с
Balatro/Hades нужны пиксельные эталоны — см. источники ниже.

## Методика разбора (UI-teardown)

Реф ценен не картинкой, а **вычлененным принципом**. Разбирая экран, отвечаю по осям:

1. **Зоны** — на какие крупные области поделён экран? Что где живёт и почему.
2. **Иерархия** — что притягивает взгляд первым? Чем сделан акцент (размер / цвет /
   контраст / позиция), а не «покрасивше».
3. **Плотность** — насколько плотно набито? Где воздух, где его намеренно нет.
   (Balatro плотный, но читаемый — вот баланс.)
4. **Ритм и сетка** — одинаковы ли зазоры между однородными блоками? Кратны ли шагу.
5. **Состояния** — как показаны hover / disabled / selected / недоступно.
6. **Читаемость** — размер шрифта относительно важности; не «плакат», не мелочь.
7. **Что тащим к себе** — 1–3 конкретных приёма, применимых к НАШЕМУ экрану.
   Именно этот пункт — смысл разбора. Без него это просто картинка.

Анти-цель: «мне нравится». Цель: «вот приём X, вот куда его у нас применить».

## Источники (проверять актуальность при заходе)

Каталоги геймдев-UI:
- **Game UI Database** (gameuidatabase.com) — крупнейшая база по экранам и паттернам,
  фильтры по типу экрана/жанру.
- **Interface In Game** (interfaceingame.com) — скриншоты UI по играм и категориям.

Пиксель-арт / инди-специфика:
- Витрины пиксельных UI-паков на itch.io и Asset Store (в т.ч. наш Honeti) — как
  автор задумал компоновку.
- Разборы UI Balatro / Hades / StS в статьях и видео (teardown-контент).

Правило: из источника вытаскиваю **принцип**, кладу картинку + разбор. Ссылку без
разбора не считаю рефом.

## Как я этим пользуюсь

Садясь за экран (напр. фикс RewardScreen):
1. Открываю `reward/` — читаю картинки и разборы.
2. Сверяюсь с методикой (зоны/иерархия/плотность) — что у нас проседает.
3. Тащу конкретные приёмы из «что тащим к себе».
4. Держу решения в рамках нашей токен-системы (`tokens.semantic.uss`), не хардкод.
